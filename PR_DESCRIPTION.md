# PR: Transaction & Expense-Splitting Foundation (Layered Architecture, Auth Stub, Test Infra)

## Summary of Changes

Establishes the initial production backend for FinTrack API on the MEAN stack, across three logical commits:

1. **`chore(standards)`** — `CLAUDE.md` (mandatory project standards: layered architecture, integer-cents money, Winston-only logging, `req.user.id` multi-tenant scoping, Jest/Supertest testing, hard constraints on deletes/participants) and `.claude/rules/transactions.md` (directory-scoped rules for `transactions/`, `expenses/`, `expense-splitting/`).
2. **`refactor(transactions)`** — `src/transactions/` split into 5 layers (`model` → `repository` → `service` → `controller` → `routes`): `CREDIT`/`DEBIT` enum, `amountCents` as a non-negative `Number.isSafeInteger`, compound index `{ userId: 1, createdAt: -1 }`, Winston structured logging throughout, and `deleteByUserId` — a single-tenant "delete all of my own transactions" exception to the no-bulk-delete rule, scoped strictly to an authenticated `req.user.id` and defensively guarded against a falsy `userId` (which Mongo would otherwise treat as an unfiltered delete).
3. **`feat(expenses)`** — `src/expense-splitting/`: a `SharedExpense` model/repository/service/controller/routes stack supporting `EQUAL`/`CUSTOM` splits, deterministic remainder-cent distribution, and `getPendingBalances(userId)` — a pairwise net-balance calculation across all of a user's shared expenses via deterministic greedy settlement + cross-expense aggregation. Also adds `src/app.js` (Express app wiring), `src/server.js`, and `src/middleware/auth.js` (an explicitly-labeled placeholder auth middleware, since no real auth exists yet).
4. **This PR's uncommitted delta** — `tests/setup.js`, `tests/expenseSplitting.test.js`, `tests/transactionScoping.test.js` (closes a pre-existing zero-test-coverage gap on the transactions feature), `jest`/`supertest`/`mongodb-memory-server` devDependencies, `npm test` wired to `jest --runInBand`, and removal of a superseded ad-hoc controller test file.

## Known Trade-offs / Deferred Work

- **Auth is a placeholder.** `src/middleware/auth.js` trusts a client-supplied `x-dev-user-id` header. This is explicitly documented in-file as `STUB AUTH MIDDLEWARE — PLACEHOLDER ONLY` and must be replaced with real JWT/session verification before any non-local deployment.
- **No update/delete endpoint for shared expenses yet.** `updateParticipants` is implemented and unit-tested at the service layer (enforcing the ≥2-participants and settled-expense guards) but is **not wired to a route** — deferred per explicit scope decision, not an oversight. See Peer Review Simulation #3 below.
- **Error responses are a blanket 400.** `src/middleware/error-handler.js` maps every thrown `Error` (validation failure, not-found, IDOR-denied) to HTTP 400. No typed error classes exist yet to distinguish 400 vs. 404 vs. 409. Consistent with the existing `transaction.service.js` pattern; flagged as a follow-up, not fixed here.
- **`getPendingBalances` does not exclude settled expenses.** See Peer Review Simulation #2 — currently harmless (nothing ever sets `settledAt`), but latent.

## Peer Review Simulation

*(Written as if reviewing a teammate's PR — actionable comments with file/line anchors.)*

**1. `src/expense-splitting/shared-expense.controller.js:5` — domain issue, penny-loss risk at the API boundary (the kind of thing AI-generated code tends to miss).**
> `createSharedExpense(req.user.id, req.body)` passes `totalAmountCents`/`shareAmountCents`/`paidAmountCents` straight through from the request body. We validate that they're safe integers, but we don't control *how the client produced them*. If a frontend (ours or a third party's) computes cents client-side as `dollars * 100` — e.g. `19.99 * 100`, which in IEEE-754 floating point is `1998.9999999999998`, not `1999` — that request gets a generic 400 `"totalAmountCents must be a non-negative safe integer"` instead of succeeding, and the failure mode is opaque to whoever's debugging it. Recommend: (a) document in the API contract that cents must be pre-rounded with `Math.round`, never truncated multiplication, and (b) consider a shared `dollarsToCents(dollars) => Math.round(dollars * 100)` utility exported from wherever we eventually put currency-boundary conversion (per `CLAUDE.md` §2, that conversion should only ever happen at the API boundary — right now no such helper exists anywhere in the codebase, so every future caller is on their own to get this right). This is the classic "off by one cent" bug class that unit tests using clean integers (like ours) won't ever catch.

**2. `src/expense-splitting/shared-expense.service.js:207` (and `shared-expense.repository.js:18-22`) — correctness gap: `getPendingBalances` doesn't exclude settled expenses.**
> `getPendingBalances` calls `findAllForMember(userId)`, which returns *every* expense the user is party to with no filter on `settledAt`. The model has a `settledAt` field specifically so a future settle/reversal flow can mark an expense as paid off (per the hard constraint that settled expenses need an explicit reversal, not a silent delete) — but nothing here excludes settled expenses from the "pending" balance calculation once that flow exists. Right now this is latent (nothing ever sets `settledAt`), but it will silently produce wrong balances the moment a settle endpoint ships, and it's an easy thing to miss because there's no failing test today. Recommend adding `settledAt: null` to the `$or` query in `findAllForMember` now, before the settle flow lands, so the two features can't get out of sync later.

**3. `src/expense-splitting/shared-expense.service.js:97-132` — `updateParticipants` is exported but unreachable from the API.**
> This function correctly enforces the ≥2-participant and settled-expense guards (and has unit tests), but no controller/route calls it — `shared-expense.routes.js` only wires `POST /` and `GET /balances`. That means the business rules it implements are currently only exercised by directly-invoked unit tests, never by an actual HTTP request, so a regression here wouldn't be caught by any integration test. Either wire a `PATCH /api/expenses/:id` route now, or if it's intentionally deferred, add a `// TODO` comment at the export site and a tracking ticket reference — otherwise this reads as dead code to the next person who finds it, and dead code with business-critical validation logic is the kind of thing that quietly rots (e.g. someone "cleans up" what looks like an unused export and we lose the guard with no test to catch it).
